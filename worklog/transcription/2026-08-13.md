# WORKLOG transcription — 2026-08-13

## 一次収録から「原本＋2エンジン転写＋リハーサル記録PDF」までを一本の配管に通した

<!-- model: Claude Opus 5 (1M context), cwd: media-scribe-workflow, duration: 約3日（2026-08-11〜13） -->

### TL;DR

2026-08-09 レオケ合同練習（映像9本 33GB＋別録りL/R 各5本）を素材に、**同期済み全長
マスター → 人が確定させた章立て → 無劣化カットで原本を凍結 → 2エンジン転写 →
Phase 1/2 のPDF記録**まで通した。新規ツール7本・改修2本を6コミット。

最大の収穫は**アーキテクチャの確定**で、「原本＝全記録から開始前・休憩・終了後を
除いたもの」というユーザーの主張を採ったことで、**SRT の再タイミングが不要になった**
（切ってから転写すれば時刻系が1つで済む）。最大の失敗は**相互相関の符号を逆に読んで
32GBを1回無駄に書き出した**こと。

### 決まったこと（設計）

**1. 原本は編集後。生素材は保存層。**
カメラをいつ回し始めたかは合奏の性質ではない。記録の境界は出来事の側で定義する
（アーカイブ学の appraisal）。この前提を採ると転写を編集の後ろに置けるので、
`srt-retime` が要らなくなる。代償は「編集の凍結」で、後から切り直すと下流が全部
作り直しになる。だから **Chaptr での確認を明示的な凍結点**として扱う。

**2. 一次資料は メディア + `.words.json` + `.meta.json`。`.srt` は派生。**
SRT は規格として (a) 確信度を持てない (b) 来歴を書く場所がない (c) cue 分割が表示上の
編集判断で観測単位へ戻せない (d) 話者・同時発話を表現できない。`to_srt_vtt()` と
`save_as_json()` が同じ result から出る以上、SRT は決定論的に再生成できる派生物。

**3. 二段構えの転写。** 区間検出用の作業用転写（速い distil・使い捨て）と、
原本確定後の本転写（large-v3 + Deepgram）を分ける。作業用を残すと「どっちが正か」で
事故るので明示的に捨てる。

### ハマったこと（全部実測で潰した）

**distil モデル + hotwords = 出力が丸ごと空**
Kotoba v2.0 に 741文字の hotwords を渡すと segments=0、SRT 0バイト。しかも
**exit code は 0 で words.json は 707KB 出る**（VAD の無音区間が入っている）ので
成功に見える。3分スライスで A/B/C/D の切り分けをして特定。distil はデコーダ2層で
プロンプトを扱えない。→ 自動無効化＋dry-run で警告。

**長尺 + VAD で cue 終端が引き伸ばされる**
数秒の発話が 1086秒の cue になる。原因は2段構え: (a) VAD が無音を除いた圧縮タイム
ラインでデコードして実時間へ戻す (b) **Silero VAD が音楽を発話と判定する**ため演奏
区間に無音マークが立たず `nonspeech_sections` での切り詰めが効かない。
`max_speech_duration_s` は stable-ts が独自 VAD 処理をしていて効かなかった。
`--chunk 10` で誤差を chunk 長に頭打ちさせ、残りは `srt-cap-spans`（発話速度を
同じファイルから実測して終端を抑える）で解決。**cue の開始は信頼できる、壊れるのは
終端だけ**という観察が鍵。

**whisper-remote の `--orchestra` プリセットにループ対策が入っていなかった**
3.7h の素材で同一文が **4348回**。20万文字＝発話 11.8 時間分という不可能な出力。
`condition_on_previous_text` が true のままだったため。`--meeting` には元から
入っていたので、音楽混在という最もループしやすい条件のプリセットの抜けだった。
`--no-condition` で 1117 cue・2万文字、処理時間も 4410秒→664秒（1/7）。
**文字数が両エンジンでほぼ一致（20760 vs 20775）したのが健全性の指標**になった。
→ `~/.config/zsh/functions/whisper-remote.zsh` の orchestra プリセットを修正済み。

途中「ループ検出が犯人」と誤診した。検出器は本物のハルシネーションを消していただけで、
真因は生成側。ただし検出器は冒頭の実質的な発話まで巻き込んでおり、両方に問題があった。

**Demucs は話し声に効かない** — 歌声分離モデルなので。ただし今回は真因がループだった
ため、Demucs の評価自体は保留（プリセットのヘルプには非推奨と書いた）。

**Deepgram の `numerals` は日本語で効かない** — パラメータ true でも「二十四小節」。
→ `srt-normalize-numbers` を派生層に作った。

**keyterm のトークン見積もりが甘かった** — `文字数/2` で 295 と見て送信し、400 で
拒否された（実際は 742）。日本語1文字≒1トークン。送信前判定に変更。

### L↔R が 29ms ずれていた（聴取で発見）

ユーザーが最終 MP4 を聴いて「左が遅れている気がする」と指摘。実測すると
**12〜29ms、しかも時間とともに増える（1.5ppm）**。原因は設計にあった:
各chを映像へ個別同期しているのに、**L↔R の相対関係を一度も検証していなかった**。
各chの対映像残差は tolerance 0.5s に対し十分小さく PASS する。しかし人間の耳は
L/R 間の差を 1〜2ms で音像の偏りとして知覚する。**映像基準の許容値を流用したのが誤り**。

→ `rehearsal-sync` に `assert_channels_coherent`（既定 5ms）を追加。現行データに
かけると 7/7 地点で NG になり、残差が時刻とともに増える様子も出る。

**符号を逆に読んで32GBを無駄に書いた。** 「R が遅れている」と報告して R をさらに前へ
ずらし、24.6ms → 52.3ms に悪化させた。ユーザーの最初の指摘（左が遅れている）が
正しかった。以後は推論に頼らず、(1)既知量を人工的に遅らせて符号を確認 (2)短い区間で
定数補正を試験 (3)atempo の向きを誇張値で確認、と3段階すべて実測してから本適用した。
結果は平均 24.6ms → 3.8ms。

### 検出の精度（人の確認が要る水準）

`segments-detect` と人が確定させたチャプターの一致率は **52.4%**。誤りは2型:

- **休憩中のざわめきを演奏と誤検出**（`--QK` 2区間・33.5分）。高音圧・広帯域・
  ASR無出力で、音響特徴だけでは演奏と区別できない。高域比 0.075 を根拠に「演奏の
  可能性が高い」と誤って断定した。判別には倍音構造や音符の立ち上がり密度が要る。
- **演奏に重ねた指示で「トーク」に倒れる**（約60分）。音量が合奏レベルなら演奏を
  優先する条件が必要。スキルに既知の弱点として書かれていたもの。

今回のチャプターは、この改良のための教師データとして使える。
